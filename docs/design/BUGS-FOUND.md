## 一、四个已确认的真 Bug

### Bug 1：`MAX_STEP_RATIO` 单帧位移截断

| 项 | 内容 |
|---|---|
| 位置 | `core/DampedSpring.java` |
| 引入 | 早期移植时自行添加（**原始 JS 版没有**） |
| 现象 | 大位移时每帧触发截断 → 每帧清零速度 → 「走一半、停一下、再走一半」 |
| 用户原话 | 「删除到上一行走到二分之一处会停顿一下」 |
| 数值痕迹 | 那个「二分之一」就是 `0.5` 这个系数 |

**触发条件（关键）**：

```
平时   dt ≈ 8ms,  animationLength = 0.05  →  单帧走 13.6%  < 50%  不触发
卡顿时 dt 被钳到 33.3ms                   →  单帧走 74.5%  > 50%  触发截断
```

**越卡越锯齿** —— 高延迟和截断互相放大。

**修复状态**：✅ **v0.5.0 已删除**（`6bed09d`）

---

### Bug 2：`lastNanos` 空闲后第一帧 dt 拉满 33ms

| 项 | 内容 |
|---|---|
| 位置 | `ui/CaretAnimator.java` → `wakeUp()` |
| 现象 | 停手几秒后第一次操作，第一帧 `dt = min((now-lastNanos)/1e9, MAX_DT)` 直接等于 `MAX_DT = 1/30 ≈ 33.3ms`（正常 8ms，大 4 倍） |
| 后果 | `c = exp(-(4/len)·dt)`，dt=0.033 时一帧衰减 93% → 等于「瞬移」 |

**数值对照**（`animationLength = 0.05`，`o = 80`）：

```
dt = 0.008 → c ≈ 0.527   每帧衰减 47%，动画跨多帧展开
dt = 0.033 → c ≈ 0.070   一帧衰减 93%，等于瞬移
```

**佐证**：快速连续删除时流畅（`lastNanos` 每 8ms 更新，dt 正常），
停顿后第一次删除才卡 —— **这个「越连续越顺」的反差正是证据**。

**修复状态**：✅ v0.5.0 用 `RECOVERY_GAP_SECONDS` 兜底覆盖

---

### Bug 3：`smoothedDt` 空闲期间被污染

| 项 | 内容 |
|---|---|
| 位置 | `ui/CaretAnimator.java` → `tick()` |
| 机制 | 空闲时调度降到 120/600ms，但 `tick()` 仍在跑，每次 dt 被 `MAX_DT` 截成 33.3ms，**无条件喂给平滑器** |

```java
smoothedDt += (dt - smoothedDt) * 0.25;
double effectiveDt = Math.max(dt, smoothedDt);   // ← 取 max
```

**恢复需要约 12 帧**：

```
第 1 帧 0.0333 → 0.0270  （仍是正常值的 3.4 倍）
第 3 帧 0.0187 → 第 10 帧 0.0094 → 约 12 帧后才接近 8ms
```

`12 帧 × 8ms ≈ 100ms` 的异常 dt。**只修 Bug 2 不够，因为 `effectiveDt` 取的是 `max(dt, smoothedDt)`。**

**修复状态**：✅ v0.5.0 已覆盖

---

### Bug 4：切屏回来 `fromIdleTier` 判据失明

| 项 | 内容 |
|---|---|
| 位置 | `ui/CaretAnimator.java` → `wakeUp()` |
| 判据 | `fromIdleTier = currentDelayMs > MAX_ADAPTIVE_DELAY_MS`（> 40） |
| 盲区 | ① 开常驻刷新时 `currentDelayMs` 恒为 8 → 永远 false<br>② 窗口失焦时 AWT 延迟派发 `invokeLater`，`currentDelayMs` 可能仍在活跃档 → 也是 false |
| 后果 | 切屏回来看似「卡一下」，三个修复全被跳过 |

**修复状态**：✅ v0.5.0 增加了按真实间隔 `rawDt > 100ms` 的第二道兜底

## 二、被发现但**不是** Bug 的（避免重复排查）

### ❌ 「归一化不对称导致斜缎带」—— 是原版特性

`TrailCorner.jump()` 用 `dx/width`（2px）和 `dy/height`（32px）归一化，
分母差 16 倍。**但原版 JS 就是这么写的**，反推验证：

| 操作 | VS Code (w=8,h=20) | IntelliJ (w=2,h=32) |
|---|---|---|
| 同行 1 字符 | len = 1.00 | len = 4.00 |
| 删除到上行行首 | len = 37.5 | len = 150 |

**VS Code 上同样是 37.5，同样远超阈值 8，同样走长动画。这是设计。**

「斜缎带」在本机更明显是因为**光标只有 2px 宽**（VS Code 是 8px），
细线一拉就成了斜条 —— **平台视觉差异，不是逻辑错误**。

### ❌ 「`0.85` 追赶系数太保守」—— 是 EDT 自适应设计

```java
int adaptive = (int) Math.round(smoothedIntervalMs * 0.85);
```

意图是让调度频率**跟随 EDT 实际交付能力**。若 EDT 只能给 20ms，
按 8ms 提交只会让任务堆积后被 `framePending` 丢弃，**反而更浪费**。

### ❌ 「`fromIdleTier` 打字时永不重置」—— 有 `tick()` 内兜底

`tick()` 里已有 `if (rawDt > RECOVERY_GAP_SECONDS)` 按真实间隔重置，
**打字时不会误触发，真正空闲会捕获**。只看 `wakeUp()` 会漏掉这段。

### ❌ 「重绘面积是瓶颈」—— 实测否定

```
面积 157290px → fps 141
面积   2345px → fps  8.9     ← 面积小 67 倍，反而慢 15 倍
```

### ❌ 「GC 停顿」—— 实测否定

```
GC(31) Pause Young  6.639ms
GC(32) Pause Young  7.344ms
GC(33) Pause Young 15.429ms
Full GC: 0 次
```

最长 15ms，而卡顿记录是 916ms ~ 31.7 秒。**差 2000 倍，不是原因。**

### ❌ 「插件绘制太慢」—— 实测否定

| 指标 | 实测值 |
|---|---|
| 12 层辉光绘制 | **0.05ms/帧**（占 8ms 预算的 0.6%） |
| 完整 Swing paint | **0.09ms/帧**（占 1.1%） |
| 插件占 EDT 采样 | **3.26%**（45 分钟 JFR，9641 采样） |
| `drawQuadGlow` 占 EDT | **2.40%** |

### ❌ 「EDT 被 IDEA 抢占」—— 部分成立但不是主因

45 分钟 async-profiler 数据（1941 采样）：

```
EDT 上 96.7% 是 IDEA 自身：IdeEventQueue + WriteIntentReadAction
插件仅 3.3%
```

**但开省电模式（关闭后台任务）用户仍报卡** → 不是主因。

### ❌ 「GPU 渲染能解决」—— 技术上不可行

| 障碍 | 事实 |
|---|---|
| JBR 25 无 GPU 管线 | `D3DPipeline` / `OGLPipeline` 均 **不存在** |
| 光标面积 | 仅 **2×32 = 64 像素**，GPU 固定开销远超收益 |
| Swing 限制 | `JComponent` 无法嵌入 Skiko/Compose 画布 |
| `acceleratedMemory` | 返回 `-1`（无加速内存） |

## 三、上游 v0.5.0 额外修的问题

来自 `6bed09d` 提交信息与代码 diff：

| 项 | 内容 |
|---|---|
| **`MIN_ANIMATION_FRAMES = 6.0`** | 强制「动画至少跨 6 帧」→ 短移动时四角时长被抬到同一值，**梯度消失，光标只平移不拉伸**。v0.5.0 **已删除** |
| **每编辑器一条调度线程** | 标签页一多就一堆线程空转。改为**全局 `RenderScheduler`**，只投递一次 `invokeLater` |
| **fps 统计把空闲算入分母** | 导致日志帧率严重偏低（README 踩坑 #21） |
| **控制台静态光标 120ms 无条件重绘** | 改为**仅在移动时重绘** |
| **前缘吸附 0.02 → 0** | 对齐原版 v1.2.7 |
| **逐像素坐标** | 改用**浮点坐标**，消除拖尾收尾时的跳动 |
| **默认隐藏原生光标** | 改为**保留原生光标 + 叠加拖尾**（对齐原版 `hideNativeCursor: false`），新增 Tools 菜单开关可切回 |

## 五、仍未解决

用户反馈**安装原版 v0.5.0 后「体验有点卡」**。

已排除：绘制开销、GC、重绘面积、EDT 后台抢占、GPU。

**待查方向**：

1. v0.5.0 改为「保留原生光标 + 叠加拖尾」，**两层光标叠加**可能导致视觉重影/卡顿感
2. 多光标支持（上限 64）可能引入额外开销
3. `RenderScheduler` 全局单线程的调度策略与旧版不同
4. 真实 EDT 交付能力 vs 8ms 期望值的差距

**下一步建议**：用 v0.5.0 自带的新菜单开关
（Tools → 隐藏原生光标）做 A/B 对比。
