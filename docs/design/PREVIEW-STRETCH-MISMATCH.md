# 预览窗把「跨行」的拉伸套在了「单行」标题下

## 现象（用户实测反馈）

- 单行快速输入：光标**不会**明显拉伸变长
- Enter 到下一行：拖尾**很长**
- 单行删除的预览窗：**拉得很长，很诡异**

结论：**实际使用是对的，预览窗失真。**

## 两套分支的真实算法（TrailCorner.jump）

短跳判据：`sameLine && charsMoved <= typingMaxChars(3)`

### 单行短跳 —— 读 trailFactors

```
animationLength = shortAnimationLength × trailFactors[rank]
```

用户参数（k=8, smooth=0.2, shortAnim=0.11s）：
```
deriveTrailFactors(8.0, 0.2) = [1.00, 0.74, 0.45, 0.26]
四角时长 = [110, 81, 50, 29] ms    最长/最短 = 3.85x
```

### 跨行 —— 完全不读 trailFactors

```
leading  = animationLength × (1 - trailSize)
trailing = animationLength
priorities: rank0 = trailing, rank1 = 中点, rank2/3 = leading
```

用户 `trailSize = 1.0` ⇒ **leading = 0**：
```
四角时长 = [280, 140, 0, 0] ms
```

前缘两角**瞬时吸附**，后缘拖 280ms ⇒ 不规则四边形，视觉上非常明显。

## 为什么预览窗看起来很夸张

预览窗每帧把光标从 A 点整体跑到 B 点，用**整段行程**展示拉伸；
而真实单行每帧只挪**一个字符宽**，且四角最短也有 29ms（约 3.6 帧）。

即：预览浓缩了「跨行」的大位移 + 长时长，却挂在「单行输入输出」这个组标题下。
**这是预览模型的失真，不是运行时行为错了。**

## 参数职责（三者互相独立，且会互相抵消）

| 参数 | 作用域 | 实际效果 |
|---|---|---|
| `stretchRatioK` | 只影响 trailFactors | 只调单行四角梯度比 |
| `animationLength` | 整体时长基准 | 缎带 0.28s / 基础 0.10s，影响最大 |
| `trailSize` | 只影响跨行 | 1.0 = 前缘瞬时吸附 |

### 关键发现：k=8 其实没被充分利用

```
k=4.5 → base [1.00, 0.72, 0.42, 0.22] → smooth0.2 → [1.00, 0.78, 0.53, 0.38]
k=8.0 → base [1.00, 0.69, 0.35, 0.12] → smooth0.2 → [1.00, 0.74, 0.45, 0.26]
```

最短角 0.38 vs 0.26 —— 但因为 `round2` 取整 + 输入平滑把梯度朝 1.0 压，
k 从 4.5 拉到 8.0 的净效果很小。**「输入平滑」和「拉伸强度」是互相抵消的两个参数**，
面板上没有任何提示说明这一点。

## 待修（下一步做光标大小实时预览时一并处理）

1. **预览窗必须区分「单行」和「跨行」两套算法** —— 现在用的是简化模型，
   把跨行的长位移套在了单行组标题下。
2. **面板文案要说明 k 与 smooth 的抵消关系** —— 否则用户把 k 调到 8 却看不到变化。
3. `trailSize = 1.0` 时跨行前缘时长恒为 0，这是一个**未在 UI 里解释**的强效果。
