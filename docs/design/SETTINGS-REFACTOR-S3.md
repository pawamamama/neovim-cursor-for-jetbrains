# 设置面板重构 S3 —— createPanel() 拆组

## 做了什么

`createPanel()` 原本是一个 465 行的 lambda，9 个组平铺在里面。加一个新参数要在
400 多行里找位置、改缩进、补逗号，每次都要重读一遍上下文 —— 这才是「加功能容易坏」
的真正原因，不是代码量本身。

拆成 11 个私有方法，`createPanel()` 从 465 行降到 **50 行**：

| 方法 | 内容 |
|---|---|
| `buildVersionRow(Panel)` | 顶行：版本号 + 使用提示 + PluginInfoBar |
| `buildPresetRows(Panel)` | 预设下拉 / 一键恢复 / 自定义预设三动作 |
| `buildMasterGroup(Panel)` | 总开关（4 项） |
| `buildInlineGroup(Panel)` | 单行输入输出 + 行内预览窗 |
| `buildCrossGroup(Panel)` | 多行缎带 + 跨行预览窗 |
| `buildColorGroup(Panel)` | 颜色（纯色 + 不透明度） |
| `buildCursorGroup(Panel)` | 光标（宽度 / RGB / 高度） |
| `buildGlowGroup(Panel)` | 辉光（4 项） |
| `buildFadeGroup(Panel)` | 淡出（2 项时长） |
| `buildExperimentalGroup(Panel)` | 实验性（折叠，渲染模式） |
| `buildDiagGroup(Panel)` | 高级诊断（折叠，2 项） |

新增一组 = 写一个方法 + 在 `createPanel()` 里加一行。

## 踩到的坑（重要）

### 组的**渲染顺序**由「谁先完成 group() 注册」决定，不是源码书写顺序

原版把 `光标（尺寸 / 颜色效果）` 组的 `panel.group(...)` 写在了
`辉光` 组的 lambda 体**内部**。看起来像嵌套，实际不是 —— 因为它用的是
`panel` 而不是辉光的 `g`。

但 `DialogPanel.group()` 是**等回调跑完才把组挂到父容器**的。于是内层那个组
先挂、外层辉光后挂，实际渲染顺序是：

```
颜色 → 光标 → 辉光 → 淡出
```

而不是源码里看起来的「辉光在前」。

拆成两个独立方法并按「光标 → 辉光」写调用后，顺序自然就对了；但一开始我按
源码观感写成了「辉光 → 光标」，渲染顺序变成 `颜色 → 辉光 → 光标`，
全部控件的遍历索引跟着挪，探针里按固定索引定位的地方立刻串台
（VRegr2 的 R-8 变好、R-11 变坏，净效果 −1）。

**结论：`createPanel()` 里各组的调用顺序是有语义的，改动前必须比对组件树。**

### 验证手段：组件树逐位比对

不要只比「有多少个滑块 / 有多少个复选框」—— 那会掩盖顺序差异（第一版就是这样
漏掉的，因为对比脚本把两边的清单都排序了）。

正确做法是把整个面板按「路径 + 深度 + 内容」dump 出来做逐行 diff：

```
d1 0.55.0 JBLabel LABEL (颜色)
d0 0.56   JLabel LABEL (拖尾颜色)
d1 0.62.0 JBLabel LABEL (光标（尺寸 / 颜色效果）)
d1 0.76.0 JBLabel LABEL (辉光)
```

重构后 79 条条目与重构前**逐位一致**（路径、深度、文本全同）。

## 结果

- `createPanel()` 465 → 50 行
- 9 个组 + 2 个辅助区全部独立成方法
- 13 个滑块、9 个复选框、3 个下拉、2 个 ColorPanel 的数量与**顺序**全部不变
- 组件树 79 条逐位一致
- 45 个探针无一变差（基线 6 条已知红保持不变）

## 已知红（基线就有，非本轮引入）

VRegr2 的 R-5 / R-6 / R-8 / R-15 / R-17 / R-17c 是 `typingSmoothness`
相关的既有缺陷，重构前 6 条、重构后仍 6 条。
