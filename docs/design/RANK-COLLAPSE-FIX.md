# rank 塌缩：为什么单行打字画不出斜缎带

> 修复版本 0.9.77 · 探针 `VRankCollapse` · 由用户观察「VS Code 上游手感更好」触发

---

## 一、一句话结论

`SpringTrail.assignRanks()` 用「比它小的有几个」计数分配 rank，
**对齐度相等时双方都不计数** → 纯轴向移动时同侧上下角拿到同一个 rank →
同速 → 四条边全部垂直 → 画出来只能是矩形/等腰梯形，斜度恒为 0。

---

## 二、rank 是什么

每个角点需要知道自己「在运动方向上有多靠后」。最靠后的角拖得最久，最靠前的角收得最快。
这个「靠后程度」就是 rank（0 = 最靠后，3 = 最靠前），它决定动画时长：

```
短跳分支：animationLength = shortAnimationLength × trailFactors[rank]
                                trailFactors = {1.0, 0.72, 0.42, 0.22}

跨行分支：rank >= 2 → leading（快）    rank == 1 → 中值    rank == 0 → trailing（慢）
```

**关键：rank 必须互不相同**。两个角拿到同一个 rank，就会有完全相同的时长，
它们每一帧走过的距离一样 —— 这两点之间的距离永远不变。

---

## 三、塌缩是怎么发生的

原实现：

```java
// SpringTrail.assignRanks()（0.9.77 之前）
for (int i = 0; i < 4; i++) {
    int rank = 0;
    for (int j = 0; j < 4; j++) {
        if (alignment[j] < alignment[i]) {   // ← 相等时不计
            rank++;
        }
    }
    corners[i].jump(..., rank);
}
```

打字右移一个字符时，四个角点相对运动方向的对齐度是：

```
TL = -0.71    TR = +0.71    BR = +0.71    BL = -0.71
         ↑                              ↑
      左边两个相等                  右边两个相等
```

跑一遍计数：

| 角 | 比它小的有几个 | rank |
|---|---|---|
| TL (-0.71) | 0 个（BL 相等，不算小） | **0** |
| BL (-0.71) | 0 个（TL 相等，不算小） | **0** |
| TR (+0.71) | TL、BL 两个 | **2** |
| BR (+0.71) | TL、BL 两个 | **2** |

**rank 只有 2 档（0 和 2），中间两档 1 和 3 从来不会被用到。**

---

## 四、为什么塌缩就出不来斜缎带

代入 `trailFactors = {1.0, 0.72, 0.42, 0.22}`、`shortAnimationLength = 0.11s`：

### 修前

| 角 | rank | 时长 | 同侧对比 |
|---|---|---|---|
| TL | 0 | 110 ms | ← 左边两角**相同** |
| BL | 0 | 110 ms | |
| TR | 2 | 46.2 ms | ← 右边两角**相同** |
| BR | 2 | 46.2 ms | |

左边缘的上下两点同速 → 左边缘始终是**垂直线**。
右边缘同理，也是垂直线。
四条边全垂直 → 四边形只能是矩形或等腰梯形。**斜度恒为 0。**

### 修后

| 角 | rank | 时长 | 同侧差 |
|---|---|---|---|
| TL | 0 | 110 ms | ← 左边缘倾 **30.8 ms** |
| BL | 1 | 79.2 ms | |
| TR | 2 | 46.2 ms | ← 右边缘倾 **22 ms** |
| BR | 3 | 24.2 ms | |

两条竖边都倾斜了，四边形变成**平行四边形** —— 斜缎带出现了。

---

## 五、修法：排序 + 索引 tiebreak

这是上游四家 JS 版本（A `30d98f9b2`、B `LengineerC`、C `neocursor-fix`、D `cursor-trail-lite`）
一致的做法：

```js
// 上游原文（B 的 computeCornerRanks）
.sort((a, b) => {
  if (a.value === b.value) return a.index - b.index;   // ← 并列时按索引拆开
  return a.value - b.value;
})
```

本项目的 Java 实现（`SpringTrail.assignRanks()`）：

```java
// 稳定插入排序（n=4，避免 Arrays.sort 的装箱 Comparator 开销）
for (int i = 1; i < n; i++) {
    int key = order[i];
    int j = i - 1;
    while (j >= 0 && alignment[order[j]] > alignment[key]) {
        order[j + 1] = order[j];
        j--;
    }
    order[j + 1] = key;
}
for (int k = 0; k < n; k++) {
    corners[order[k]].jump(width, height, centerX, centerY, k);  // k 就是 rank
}
```

稳定排序保证「相等的元素保持原始顺序」，于是 TL(idx 0) 排在 BL(idx 3) 前面，
**rank 变成 0/1/2/3 四个互不相同的值**。

### 为什么 tiebreak 用索引而不是别的

1. **确定性**：同样输入永远得到同样 rank，不会这帧一种排法下一帧另一种
2. **斜度方向稳定**：tiebreak 方向恒定 → 缎带总是朝同一侧倾斜，
   不会出现「这一帧往左斜、下一帧往右斜」的抖动
3. 四家上游都用索引，观感已经被大量用户验证过

## 六、实测对照

探针 `VRankCollapse`，光标 2×32，五个方向：

| 场景 | 修前 rank | 档位 | 修后 rank | 档位 | 上游 |
|---|---|---|---|---|---|
| 打字 →（同行） | `0 2 2 0` | **2** | `0 2 3 1` | 4 | `0 2 3 1` ✅ |
| 删除 ←（同行） | `2 0 0 2` | **2** | `2 0 1 3` | 4 | `2 0 1 3` ✅ |
| 下一行同列 | `0 0 2 2` | **2** | `0 1 2 3` | 4 | — |
| 上一行同列 | `2 2 0 0` | **2** | `2 3 0 1` | 4 | — |
| 斜跳 ↘ | `0 1 3 2` | 4 | `0 1 3 2` | 4 | `0 1 3 2` ✅ |

**四个纯轴向方向全部从 2 档修到 4 档，拉平/删除两个方向与上游逐位一致。**

---

## 七、为什么斜跳一直正常

斜跳（同时有 x 和 y 位移）时四个对齐度天然互异：

```
斜跳 ↘：  -0.91 / -0.41 / 0.91 / 0.41
```

没有并列，计数法自然给出 `0 1 3 2` 四档。所以塌缩只在**纯水平 / 纯垂直**移动时发生。

这正好对上用户的原始描述：

> 「特定情况下是缎带拉伸效果，但更像斜缎带」

—— 只在斜跳/跨行时能看到缎带，单行打字看不到。

---

## 八、为什么 PhysicsParity 没红

`PhysicsParity` 是逐字节比对的黄金基准，但它**直接给 `TrailCorner.jump()` 传 rank**，
不经过 `assignRanks()`。所以这次改动不触碰它的输入，基准保持 PASS。

这是设计上的好运气：如果基准走了完整链路，这次修复会让它大面积变红，
而那种红是**预期内的行为变好**，反而不该当回归看。
