## 二、代码取证结果

### 2.1 【决定性事实】全仓库无任何 IME / 组合输入处理

对 `src/**/*.java` 搜索 `IME|InputMethod|composition|Composition|inline|Inlay`：

```
实际命中 36 处，但逐条核对后【全部是误匹配】：
  - AfterimageTrail.java 的 timeNanos / lifetime（时间戳，与 IME 无关）
  - CaretAnimator.java 的 System.nanoTime()（同上）
  - RenderScheduler.java 的 nanoTime（同上）
→ 真正与输入法相关的命中数 = 0
```

**结论**：插件**从未考虑过输入法组合态**。它对"光标应该在哪个像素"的全部认知，来自每帧调用：

```java
// CaretAnimator.refreshTarget()  L806 / L821
VisualPosition vp = editor.getCaretModel().getVisualPosition();
Point p = editor.visualPositionToXY(vp);
```

**这两行在 IME 组合期间的行为，是本文档要解释的焦点。**

### 2.2 坐标来源：单一来源，但依赖平台中间态

`CaretAnimator` 类注释（L39-41）明确写着：

> 坐标系：全程使用 contentComponent 坐标系。
> `editor.visualPositionToXY()` 返回的正是该坐标系下的点，而绘制面板也挂在 contentComponent 上，
> 因此**完全不需要坐标转换**。

这段话本身是对的 —— **它排除了"我们自己算错坐标"**。但这也意味着：**平台给什么，我们就画什么，没有任何校验**。

### 2.3 已知的事件时序陷阱（代码自己记录过）

类注释（L42-46）：

> **为什么不依赖 caretPositionChanged**：实测发现删除文本等场景下，
> 光标事件可能在 `visualPositionToXY()` 数据更新之前就触发 ——
> 此时读到的仍是旧位置，而之后不会再有新事件，拖尾就会永久卡在旧位置。
> 因此改为**每个 tick 都重新读取光标位置**，事件仅用于"唤醒"。

**这条记录极具价值**：说明本项目**已经踩过一次**"事件先于坐标更新"的坑，并且用"每帧主动读"绕过了它。

但 IME 组合态是另一个形态：**不是"坐标没更新"，而是"坐标处于一个临时的、非字符边界的中间态"**。每帧主动读**救不了这种情况** —— 因为读到的确实是当前的中间态。

### 2.4 「半个字符」的可能来源（三个候选，按可能性排序）

#### 候选 A：IME 组合文本的 caret 位于**合成串内部**（最可能）

Windows 中文输入法在组合期间，IDE 会在光标处显示一个**内联组合串**（候选/拼音串）。此时：
- `getVisualPosition()` 返回的 column 可能指向**组合串中的某个位置**
- `visualPositionToXY()` 按该 column 换算出的 x，可能落在**半个字符宽**处（因为组合串的字符宽度与最终汉字不同）

→ 完全解释 O3「卡在竖笔画上」（≈半个字宽）。

#### 候选 B：`cursorWidth` 语义混用导致中心点偏移

```java
L304: private double cursorWidth;          // 字段：实际光标宽度
L826: double width = config.cursorWidth;   // 读配置（固定 2f）
L854: double newCenterX = p.x + width / 2.0;  // 中心 = 左上 + 1px
L862: cursorWidth = width;                 // 又写回字段
```

`width` 恒为 `config.cursorWidth = 2f`，与真实字符宽度**无关**。这是**设计本来如此**（不是 bug），但如果平台的 `p.x` 在某些状态下给出的是"字符左边界 + 半宽"，两者叠加就会出现半字符偏移。

**注意**：这是**次要嫌疑**，因为正常打字不出问题，只在 IME 组合态出问题。

#### 候选 C：方向键 → 坐标跳变被弹簧插值「抹平」

用户说「按右方向变向左移动」。真实可能：
- 组合态退出时，caret 从中间态跳回真实位置
- 弹簧从"错位点"过渡回"正确点"，位移方向恰好相反
- `DampedSpring` 的插值让这一帧看起来像"向左走"

→ 这是**症状的放大器**，不是根因。

## 三、为什么"卡住之后不自动恢复"

这是 O5「不稳定复现」与"卡住"能持续的关键。三个必要条件：

1. **`refreshTarget()` 有快速路径**（L812）：
   ```java
   if (!forceResync && vp.line == lastVisualLine && vp.column == lastVisualColumn) return false;
   ```
   只要 `vp` 不再变化，**就永远不再重算坐标** —— 即使真实像素位置已经变了。

2. **`forceResync` 只在内容区尺寸变化时置位**（L603-607）：
   ```java
   if (panel.getWidth() != content.getWidth() || ...) { ...; forceResync = true; }
   ```
   IME 组合态期间编辑器尺寸**不变**，所以 `forceResync` 永远为 false。

3. **caret 事件只 `wakeUp()`，不置 `forceResync`**（L509）：
   ```java
   public void caretPositionChanged(@NotNull CaretEvent event) { wakeUp(); }
   ```

**三者叠加** = 一旦 `vp` 停在某个值上，插件就认为"光标没动"，永久沿用可能错误的像素坐标。这与代码注释里记录过的"拖尾永久卡在旧位置"是**同一类结构性缺陷**，只是触发条件不同。

### 3.1 补充取证：代码里**没有**任何滚动/视口监听

对 `src/**/*.java` 搜索 `Scroll|scroll|VisibleArea|visibleArea|Viewport|viewport`：

```
命中 = 0
```

**这条很重要**：意味着"滚动编辑器"这个动作，插件**完全感知不到** —— 它既不会被唤醒，也不会置 `forceResync`。这解释了 §4.1 的 E3 实验结果（见 §3.2）。

`forceResync` 只有两个置位点（L606 尺寸变化、L1099 见 §3.2），**没有任何滚动相关路径**。

## 三之二、实验结论（2026-10-18 22:47 补充，用户实测）

用户完成了 §4.1 的四个鉴别实验，结果如下：

| 实验 | 用户结果 | 判读 |
|---|---|---|
| **E1** 英文输入法打同样无效串 | **只有中文有** | ✅ **确证 O1/O2**：是 IME 组合态特有，与"无效字符"本身无关 |
| **E2** 保持组合态按 Esc | "不明白" | ⏸ 未取得数据（用户无法判断该看什么） |
| **E3** 滚动编辑器 | **只有切换大小时**才变化 | ✅ **确证 §3.1**：滚动无效（插件无滚动监听），只有**内容区尺寸变化**才走 L603-607 → `forceResync = true` |
| **E4** 切标签页再切回 | **没有，钉死了没动** | ✅ **确证 §3 的"永久卡住"**：切标签页不改变 `content` 尺寸，也不触发 `forceResync` |

### 关键新增观测（用户补充，价值最高）

> **"我继续输入，他跳回来了，接在那行最后"**

这一条**同时确证了两件事**：

1. **错位状态是"坐标缓存"而非"坐标算错"** —— 继续输入改变了 `vp`（column 变了），快速路径失效 → 重算 → 立刻回到正确位置。这完全符合 §3 的三条件机制。
2. **错位期间插件认为光标在某处，但真实光标其实一直在"行最后"** —— 用户说"接在那行最后"，说明 `p` 一旦重算就落到行尾，而错位期间画的位置**根本不在行尾**。

**→ 候选 A（IME 组合串内部中间态）成为唯一合理解释**：
- 组合期间 `getVisualPosition()` 的 column 指向组合串内部某个位置
- `visualPositionToXY()` 按该 column 换算出**半个字宽**的 x（对应"卡在竖笔画上"）
- 组合结束后 `vp` 本该跳回真实位置，但因**快速路径缓存**而未重算
- 直到下一次输入改变 column，才重算并"跳回来"

候选 B（`cursorWidth` 语义混用）被判为**次要**：它只能解释固定偏移，解释不了"继续输入就自愈"。
候选 C（弹簧插值）被判为**非根因**：它只放大症状。

### 3.3 修正后的机制图

```
IME 组合态开始
  └─ getVisualPosition() 返回组合串内部位置（列值 ≠ 真实光标列）
       └─ visualPositionToXY() 算出"半个字宽"的 x  ← 对应「卡在竖笔画上」
            └─ lastVisualLine/lastVisualColumn 被记为该中间态值
                 ├─ 组合结束：平台列值恢复正常，但…
                 │    └─ 【快速路径】vp 与缓存比较 → 若相等则 return false（不重算）
                 │         └─ 实际情形：组合结束后 column 可能恰好等于缓存值
                 │              → 永久沿用错误像素坐标  ← 对应「钉死了没动」
                 └─ 继续输入：column 改变
                      └─ 快速路径失效 → 重算 → 跳到正确位置  ← 对应「跳回来，接在行最后」
```

## 四、需要用户补充确认的（用于把报告变成可复现缺陷）

### 4.1 关键鉴别实验（决定是候选 A 还是 B）

| 实验 | 操作 | 观察 |
|---|---|---|
| **E1** | 切到**英文输入法**，输入同样长度的无效字符串 | 若**不出现** → 确证是 IME 组合态特有 |
| **E2** | 中文输入法下，**只打拼音不选候选**（保持组合态），然后按 Esc | 观察是否在 Esc 那一刻跳到正确位置 |
| **E3** | 出现错位时，**滚动一下编辑器**或**调整窗口大小** | 若立刻恢复 → 确证是 §3 的快速路径缓存问题 |
| **E4** | 出现错位时，**保存文件**或**切换标签页再切回** | 同上，判断是否靠 `forceResync` 恢复 |

> **E3/E4 是最有价值的两条**：如果它们能让光标"自己跳回正确位置"，就 100% 确证了 §3 的机制，修法也随之确定（在 IME 组合开始/结束时强制 `forceResync`）。

### 4.2 关于「按右方向却向左移动」（O4）

这条需要更精确的描述才能定性。可能是：
- **真实反向**：坐标跳变 + 弹簧插值（候选 C）
- **视觉错觉**：光标实际向右，但拖尾的"尾巴"在左，看起来像整体左移
- **IDE 自身行为**：某些 IME 状态下方向键被输入法窗口吞掉

建议复现时**关掉拖尾**（用 Tools 菜单开关）再试一次 —— 若关掉后方向正常，说明是插件"视觉"问题；若仍然反向，则是 IDE/IME 层面。

### 4.3 关于「10 个字符、50% 之后」（O6）

这是当前唯一的量化线索，但用户自评"好像"。建议：
- 若能给出**大约多少次输入后出现**（例如"打 10~20 个字必现" vs "几百字才一次"），可直接判断是竞态概率还是稳定阈值。

## 五、影响评估（同意用户的判断）

| 维度 | 评估 |
|---|---|
| 数据安全 | **无影响** —— 插件只画覆盖层，不改文本，不写文件 |

## 六、候选修法（讨论用，未实施）

> **机制已由 E1/E3/E4 + "继续输入就自愈"四点确证**（见 §3.2）。因此 F1/F2 不再是"盲猜"，而是对症方案。

| 方案 | 做法 | 代价 | 评价 |
|---|---|---|---|
| **F2（首选）** | `caretPositionChanged` 里置 `forceResync = true` | 一行；每次光标事件多一次 `visualPositionToXY` | **最小改动**。能消掉"永久卡住"，但**不消掉错位瞬间**（组合期间的中间态仍会被画出来） |
| **F1（根治）** | 监听 IME 组合开始/结束，组合期间**强制 `forceResync`** 或**暂停绘制** | 需确认 IntelliJ 暴露的 API（可能要用 `EditorImpl` 的 `InputMethodRequests` 或监听 `Document` 的 `composing` 状态） | **最对症**。但平台 API 不确定，需先查证 |
| **F2'（折中）** | 每帧比较 `getOffset()` 与上一帧：**offset 未变但 vp 变了** → 判定为中间态，跳过 | 一次 `getOffset()`（很便宜，已在用） | 可能有效：组合期间真实 offset 往往不变（还是那个插入点），而 vp 在变 |
| **F4（规避）** | 组合期间把覆盖层整体降不透明度 | 不改坐标逻辑 | 稳但治标 |

**F2' 值得注意**：`refreshTarget()` 里已经在读 `getOffset()`（L842，供 `charsMoved` 用）。
- 正常移动光标：offset 变、vp 也变
- **IME 组合期间：offset 不变（插入点没动），但 `getVisualPosition().column` 可能变**
- → 用 `getOffset()` 作为"真实位置"的金标准，若两者不一致则信任 offset 或跳过本帧

这是**用已经付过费的调用**（`getOffset()`）来识别中间态，成本几乎为零。
