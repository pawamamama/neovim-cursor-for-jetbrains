# 改别人的项目之前，先读它自己的教训

## 为什么有这个 skill（一次真实的、代价很大的失败）

用户要求在第三方 JetBrains 插件里「关闭光标拉伸」。

我当时**没有读项目自己的 `README` 踩坑记录** —— 尽管它就在手边，
而且用户此前还给过我链接。

然后我用两种不同方式实现了「关闭拉伸」。**两种都已被维护者试过并撤销，
并且都写在踩坑 #20 和 #19 里。** 第二次尝试（关掉前缘硬吸附）让编辑器
**卡死到用户无法工作**，最后只能全部回滚。

维护者针对我做的那件事，早就写下过结论：

> 原版在 60fps 下最短的角一帧到位，是**设计行为**而非缺陷。
> 「修复」之前先确认它真的是 bug。

不读的代价：给用户装了好几个错版本，其中一个弄坏了他的编辑器，最后整体回滚。
读的代价：一条命令。

## 规则

**当你修改一个不是自己写的项目时，维护者自己的排查记录，优先于你的分析。**
你要做的实验，他们已经做过了。

动手改任何行为之前，按这个顺序走：

1. **找到项目自己的失败记录。** 常见名字：
   - `README*` 里的章节：`踩坑`、`Lessons Learned`、`Known Issues`、
     `Gotchas`、`Pitfalls`、`Troubleshooting`、`设计说明`、`FAQ`
   - `CHANGELOG` / release notes —— **特别注意「撤销某功能」的条目**
   - `CONTRIBUTING`、`docs/`、`HISTORY.md`，以及以
     `NOTE:`、`WARNING:`、`曾`、`之前`、`不要`、`原版` 开头的代码注释
   - 维护者写的 issue / PR 正文

2. **一定要拿到那份文档的最新版。** 本地旧副本和不读一样糟。

   ```bash
   git fetch origin main
   git log --oneline -1 origin/main
   ```

   上面那次失败里，本地 README 有 **18** 条踩坑，上游 `main` 有 **21** 条。
   多出来的三条里，正好有宣判我那次改动的那一条。
   *本地 checkout 是快照；你需要的那份文档可能比你的克隆新。*

3. **对比基线之后上游做了什么。** 修法可能已经存在。

   ```bash
   git log --oneline <你的基线>..origin/main
   git diff --stat <你的基线> origin/main -- src
   ```

   读了可能发现维护者用别的方式解决了 —— 或者那个「问题」本就是有意为之。

4. **这时**才形成方案。方案成型后**再回头读一遍**踩坑记录，问自己：
   *「我要做的改动，像哪一条已有记录？」*
   如果像一条「已撤销」的记录 —— 停下，把它说出来。

## 快要重蹈覆辙的红旗信号

- 你的改动**抹平了一个梯度**，而原版是刻意做出差异的
  （逐角点/逐元素的时长、逐名次的系数）。取成统一值，往往正是维护者**删掉**的东西，
  因为它会把效果做没。
- 你的改动**关掉了某条「吸附／瞬时」路径**，改成走完整时长的动画。
  瞬时路径通常是为了「跟手」，不是 bug。
- 你的改动让**每一帧都更贵**，然后你把它称作优化。
- 项目里有**诊断模式**（禁用绘制、fps 日志、dry-run），而你还没用过。
- 你正要基于**自己算出来的数字**宣布「这是性能修复」，
  而不是**在实际运行时里测出来的数据**。
- 用户说某个行为是 bug，但项目记录里称它是**设计决定**。
  先把维护者的理由摆到用户面前，再动代码。

## 当用户说「你试试」

只有在改动**可回滚且隔离**时，「试试」才便宜。发货之前先做到这点：

1. 让用户的可用状态能按**内容哈希**找回，而不是按名字。

   ```powershell
   (Get-FileHash $artifact).Hash
   ```

   版本**名字会骗人**：上面那次失败里，一个叫 `...-0.4.3.jar` 的文件，
   里面的 `plugin.xml` 写的是 `0.4.4` —— 靠名字推理完全无效。

2. 在**独立分支**上做，从「已知可用」的那个提交切出去；
   永远不要去改「产出了用户满意那个产物」的分支。

3. 尽量用**最小 diff**，并且证明它：

   ```bash
   # 逐个 class 反编译比对；预期只有一个是不同的
   ```

   只改参数时，应当只有配置类不同。如果连嵌套 `enum` 也不同，
   先确认那只是**新增注释导致的行号表位移**（去掉行号信息再比对 `javap` 输出）。

4. **把回滚命令和安装命令写在同一条消息里。**

5. 如果改动涉及**时序、帧调度、动画常量**，直说自己在这里无法验证流畅度，
   并且有可能卡死。

## 「先读」会改变什么

那份记录里，维护者用原话写着：隐藏原生光标正是这个效果显得卡的原因；
低帧率补偿把原本有意的拉伸抹平了；以及——用户可见的缺陷，先确认它真是缺陷再修。
先读它们，能把「好几个版本都失败」变成「一句话的提问」。

## 汇报模板

当某条已有踩坑记录与你的发现吻合时，**原文引用并注明出处**。
用户更信维护者的话，而不是你的推断 —— 而且万一你判断错了，
这段引用正是他们能告诉你的依据。
