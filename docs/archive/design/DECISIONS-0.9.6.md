## 1. A：输入手感不平滑 —— 已定

### 1.1 用户原话

> 缎带 原版粉色 柔和，高对比这些**有平滑**；其余预设都**没有平滑输入而且拉伸快**
> （输入手感）**选项 2**

### 1.2 根因（数据已核实）

| 预设 | shortAnimationLength | 后缘/前缘 | 用户评价 |
|---|---|---|---|
| 原版粉色 | **0.11** | 110/24 ms | 平滑 |
| 缎带 | **0.11** | 110/24 ms | 平滑 |
| 柔和 | **0.08** | 80/18 ms | 平滑 |
| 高对比 | **0.10** | 100/22 ms | 平滑 |
| Neovide 官方 | **0.04** | 40/9 ms | 过快 |
| 社区·快 | **0.04** | 40/9 ms | 过快 |
| 社区·平滑 | **0.04** | 40/9 ms | 过快 |

**规律：short >= 0.08 → 平滑；= 0.04 → 过快。**

**根因**：那 3 个预设照抄了 Neovide / VS Code 的官方默认值 0.04。
但本插件是 125fps（8ms）+ 2px 细光标，0.04s 只有 5 帧，
四角时长 = 0.04 x {1.0,.72,.42,.22} = 40/29/17/9 ms → **前缘只有 1 帧，等于瞬移**。

这一点在 core/NeovideConfig.java:103-118 早有记录（用户自己的历史实测结论）。

### 1.3 决策

**两条同时做：**

**(a) 所有预设的 shortAnimationLength 统一到 0.11**
- 理由：输入手感是基本体验，不该成为预设的差异维度
- 预设只调拖尾风格（跨行时长 / 拖尾密度 / 辉光），不调打字手感

**(b) 新增一个独立字段：输入平滑（typingSmoothness）**
- 用户明确选选项 2 = 加独立滑块，而不是改 shortAnimationLength 本身
- 三个候选设计：
  - 方案 i：它就是 shortAnimationLength 的 UI 别名（最简，但没新增能力）
  - 方案 ii：它是一个乘数，短跳实际时长 = shortAnimationLength x 本值
  - 方案 iii：它是**独立的四角梯度系数**（脱离 trailFactors）**← 推荐**
- **推荐方案 iii 的理由**：用户说拉伸快，本质是**四角梯度太陡**（前缘 9ms vs 后缘 40ms = 4.5 倍）。
  一个输入平滑滑块应该是**调短跳分支的四角梯度**，而不是调总时长。

### 1.4 验收

- 7 个预设的输入手感全部平滑（后缘 >= 80ms）
- 新滑块能从无拉伸平滑过渡到强拉伸
- 不影响跨行分支的手感（跨行仍由 animationLength + trailSize 控制）

## 2. B：行缎带新功能 —— 已定

### 2.1 用户原话（完整）

> 缎带加一个行缎带预设（就是缎带效果全开）
> 我想一行中快速删除添加的时候，根据行数拉伸缎带慢慢变长，停止之后是那种拉伸弹簧回弹效果
> **b** 不是停止回弹就是正常回弹
> （问题1）**a** —— 就是一直长
> （重置时机）**停手后**
> 停手后后面的缎带**收缩到当前光标位置**但是要**弹**，和行缎带一样但是是**横向的加速度**
> 架构能做，就是光标扩散但是拉长；如果换行能做这效果，单行肯定能做；当然需要你调研 VS Code

### 2.2 需求精确化

**触发场景**：单行内连续快速删除 / 添加

**效果描述**：
```
连续操作时：
  拖尾长度随操作次数累积、一直变长（不设上限，或上限很高）
  形状 = 光标被扩散出去但整体拉长（不是简单的四边形拉伸）
  方向 = 横向（沿行的方向）

停手后：
  拖尾从末端向【当前光标位置】收缩
  收缩过程带【弹簧回弹】—— 会过冲一下再稳定，不是线性收回
  加速度是横向的（不是纵向）
```

### 2.3 与现有架构的关系

**现在的行为**：每次光标移动 → TrailCorner.jump() 重新设定四角的弹簧参数 → 每次独立，**不累积**。

**需要的新机制**：
1. **累积状态**：记录当前累积了多少横向位移，连续操作时递增
2. **停止检测**：判断停手（现有 anyAnimating / glowStrength 的判据可复用）
3. **收缩动画**：停手后启动一个独立的收缩阶段（现在没有这个阶段，只有 fading 淡出）
4. **回弹**：收缩要带过冲 —— **DampedSpring 是临界阻尼（不过冲），需要欠阻尼才回弹**

**风险**：DampedSpring 是临界阻尼闭式解（c = exp(-(4/len)*dt)），不会过冲。
要做回弹需要引入**欠阻尼**参数（阻尼比 < 1），这是对物理核心的改动，**风险高**。

### 2.4 需要调研的

- VS Code 版 neovide-cursor 怎么做的？（它没有这个效果，只是四角拉伸）
- 有没有其他插件做过累积拖尾 + 回弹？
- Neovide 官方的 vfx_mode（railgun / torpedo / pixiedust / sonicboom / ripple / wireframe）有无可借鉴？

**结论：这是本版最大的新功能，建议单独一个版本做，不要和 0.9.6 混。**

### 2.5 行缎带预设本身（可以先做）

预设名：**行缎带**（与缎带区分）
定位：缎带效果全开，但**只影响短跳分支**（单行内）

初步参数（待实现时调）：
```
animationLength       0.28   （跨行也慢）
shortAnimationLength  0.15   （比默认 0.11 更长，单行拉伸更明显）
trailFactors          需要更陡的梯度（如 {1.0, 0.85, 0.6, 0.35}）
```

**注意**：trailFactors 现在由拉伸强度滑块控制（4.5x），**这个预设需要覆盖它**。

### 2.6 「拉伸强度」字段定位 —— 已定（本轮确认）

用户原话：

> b 拉伸强度是新字段就得能改 所以当普通参数用

**采纳：拉伸强度 = 普通可调参数（和 glowOpacity 同等待遇）。**

1. 有自己的可调项（滑块 + 数值框），进 settings 契约与审计清单；
2. **点预设会覆盖它** —— 预设优先，规则见 §5.5；
3. 不做「只有某个预设才可见」「预设专属倍率」这类隐藏状态。

**第 3 轮确认（用户原话）**：

> 拉伸强度被预设覆盖吗？默认预设优先，只有用户自己修改之后才变成已修改
> 感觉没人改这个。其实也可以做一个拉伸强度独立但是逻辑变复杂了，不是最优先

→ **结论：预设优先覆盖，不特殊化。**

「拉伸强度独立、不受预设影响」= **未来可选**，本轮明确**不做**：它会让"已修改"判定多出一个维度（这个字段不改 → 算不算已修改？），逻辑变复杂，收益低。
记录为 backlog，**不写进任何版本的验收标准**。

### 3.3 不同步：是双入口造成的，不是状态同步 bug —— **已查明（2026-10-20 夜）**

用户说 Tools 和主设置的总开关有些设置好像没有同步。原先列的三个可能原因，逐条查过：

| 猜测 | 结论 | 证据 |
|---|---|---|
| R-01 类残留（pending 与 state 不一致） | ❌ 不是。0.9.5 的 A6/A7/A8 已修，t7 的 T-01 守着 | `run-t7-probe.ps1` 全绿；本次新增 U23 也绿 |
| ToggleXxxAction 不刷新面板 | ✅ **这是真因的一半**，但它只在「面板同时开着」时可见 | 面板是模态对话框，菜单点不到；实际表现是**下次打开面板时看到旧勾选** |
| install() 路径没走 applyConfig | ❌ 不是。所有 setter 都调 `syncConfigToStateAndPersist()` | 代码核对：setTrailMode/setHideNativeCaret/setOverlayFadeOut/setAlwaysHighFps/setEnabled 五处全有 |

**M2 加的护栏（U19–U23，在 `VerifyPanel.java`）**：

- U19：复选框数量与构建顺序（6 个）；
- U20：五个布尔全 false → reset → 一个都不许勾（显示不能残留）；
- U21：逐个只开一个 → reset → 只有它自己勾上（显示与 state 同源）；
- U22：Tools 关掉常驻刷新 → 面板显示未勾选；
- U23：面板 apply **不得**把 Tools 的 `alwaysHighFps=false` 冲回 true。

**探针有效性（变异证明，2026-10-20 夜实测）**：把 `reset()` 里的 `pending = cur;` 注释掉后，
U20/U21/U22/U23 **全部变红**（U23：`state.alwaysHighFps=true` ← 被冲回）。
恢复后 23/23 全绿。**所以这 5 条断言真的能抓这一类 bug，不是假绿。**

**真正的根因（因此 M1 就是修法）**：同一个开关有**两个入口**（菜单 + 面板），
两边各持一份快照。删掉菜单里那 5 个重复开关之后，唯一入口只剩面板，
「两处不同步」在结构上不可能再发生 —— 这比再补一条同步代码更彻底。

**必须写探针复现，不能猜。**

## 4. D：隐藏原生 + 关常驻 轻微卡 —— 已定：**做分离**

### 4.1 用户原话

> 观察到隐藏 idea 原生光标 + 关闭常驻刷新 8ms 好像会卡动画但是不明显
> 表现为**字符被提前删除**但是没有那么卡
> 但是**中文输入候选乱输入可能卡**
> 这个很难抉择

### 4.2 两个独立的症状

**症状 1：字符被提前删除**
```
文档层：字符立即删除
视觉层：覆盖层等下一帧才重绘（空闲 120ms）
→ 中间出现文字没了但光标还在旧位置的窗口
```

**症状 2：中文候选乱输入时卡**
```
IME 组合态下 caretPositionChanged 高频触发
但可能不触发我们依赖的唤醒路径（或触发了但被 forceResync 的早退吃掉）
```

### 4.3 候选方案

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| 1 | 禁止该组合 | 最简单 | 用户之前反对禁止 |
| 2 | 勾选隐藏原生 → **自动强制常驻刷新**（置灰+提示） | 消灭症状 | 用户失去省电选项 |
| 3 | 保留但加高级例外开关 | 灵活 | 用户可能仍踩坑 |
| 4 | **加强唤醒路径**（IME 相关监听 + 编辑操作监听） | 治本 | 需调研，工作量大 |

**captain 原来的倾向：方案 4 + 方案 2 的组合**
- 短期：方案 2（自动联动），保证不出问题
- 长期：方案 4（补监听），之后可以放开限制

### 4.4 用户决策（本轮确认）

用户原话：

> 重构做 d 这个一定做分离 我这个没测试好，我得好生体验一下

| 方案 | 结果 |
|---|---|
| 1 禁止该组合 | ❌ 不做 |
| 2 勾隐藏原生 → 强制常驻刷新 | ❌ **否决** |
| 3 高级例外开关（方案 2 的补丁） | ❌ 不做 |
| **分离：两开关真正独立** | ✅ **采纳** |

**分离的具体含义（按这个做，别扩）**：
- 「隐藏原生光标」和「常驻刷新」是**两个独立开关**，谁也不改谁的值；
- UI 上只给**文字提示**（例如"关掉常驻刷新时，隐藏原生光标在低频重绘下可能看起来滞后"），**不置灰、不自动改值**；
- 不做运行期联动（写配置时的隐式强制也算违规）。

> **captain 的"自动强制"提案被用户否决 —— 记录在案，不偷偷实现。**

**实施时机：冻结，等用户体验完再动**（原话「我这个没测试好，我得好生体验一下」）。

### 4.5 体验时只回答 3 个问题（其余不管）

1. 关掉常驻刷新（8ms）再开隐藏原生，**动画是不是明显变卡**？（还是原来的"轻微、不明显"）
2. 「字符被提前删除、光标还在旧位置」这个窗口**能不能截到**（录屏 0.25x 慢放看）？
3. 中文输入法候选态打字**卡到什么程度**（能不能忍 / 乱码 / 掉字）？

> 结论只影响"方案 4 要不要提前做"，**不影响分离这个决定**（分离已经定了）。

## 5. E：自定义（当前值）—— 已定：接受推荐形态

### 5.1 用户原话

> 自定义当前值有点迷惑了，看看其他人怎么做的（就是**有人想基于一个预设改**怎么办呢）

### 5.2 主流做法对比

| 软件 | 做法 |
|---|---|
| **VS Code 主题** | 显示主题名 + （已修改）标记 |
| **OBS 场景** | 带 * 号表示有改动 |
| **Photoshop 预设** | 自定义但可另存 |
| **游戏画质** | 低/中/高/**自定义**（无来源） ← 我们现在 |

### 5.3 推荐方案

```
动画预设：[缎带（已修改）]
          ├ 原版粉色
          ├ 缎带              ← 当前基于这个
          ├ Neovide 官方
          ├ ...
          ├ -----------
          └ 恢复为缎带默认值   ← 新增，一键回到预设原样
```

**优点**：保留来源信息 + 有恢复手段 + 不需要另存为新预设这种重功能。

### 5.4 决策（本轮确认）

用户答复：**接受**。

**实现要点**：
- 预设名显示为 `缎带（已修改）`：当前值与某个预设的常量逐项相等（EPS=1e-6）时显示原预设名；
- 下拉列表末尾加分隔线 + `恢复为 {原预设名} 默认值`，点它把该预设常量写回一次；
- 用户手动改过任意一个常量 → 名字立刻回到 `（已修改）` 状态，不需要点"应用"。

**不改的**：`自定义（当前值）` 这个旧标签彻底删掉（它没有来源信息，正是迷惑的来源）。

### 5.5 「预设 vs 已修改」的通用规则 —— 用户第 3 轮明确定义

用户原话：

> 默认预设优先，只有用户自己修改之后才变成已修改
> 柔和预设就是大于已修改，但是有人想要柔和+缎带他自己改就是了，标记为已修改

**规则（适用于全部 19 个参数，含拉伸强度）：**

| 动作 | 结果 |
|---|---|
| 点任一预设 | **预设赢** —— 把该预设的常量全部写回，名字变成干净预设名（`柔和`、`缎带`…），**冲掉**你之前的手工修改 |
| 手工改任意一个值 | 名字变成 `{最近预设}（已修改）` |
| 在"已修改"状态再点预设 | 还是**预设赢**，回到干净预设名 |
| 想要「柔和 + 缎带那段拉伸」 | 选柔和 → 自己改拉伸相关参数 → 名字显示 `柔和（已修改）` |

**这条规则是 E/F/B 三处的共同底座**，实现时只需要一个"当前值是否等于某预设"的判定（EPS=1e-6 逐项比较），不需要额外状态位。

## 6. F：高对比 —— 已定：**保留 + 加字段**

### 6.1 用户原话

> **高对比不错** 我试了，建议**加一个字段专门高对比**

### 6.2 理解

用户先说不明白，实测后说不错，但建议**加一个字段专门控制它**。

现在高对比 = glowOpacity 0.75 / glowLayers 10 / shadowBlurFactor 0.15。
它的特征 = **辉光亮 + 外扩小 = 锐利的辉光边缘**。

**加一个字段的两种理解**：
1. **加一个预设**（独立的 高对比 预设已经有了）
2. **加一个参数**，把辉光锐度暴露成可调项
   - 现在 shadowBlurFactor 已经在可调列表里（0.05-0.60）
   - 但用户可能想要的是辉光锐度这个**语义**，而不是外扩幅度这个物理量

### 6.3 决策（2026-10-20；第 3 轮确认：E 和 F 两件都答应）
