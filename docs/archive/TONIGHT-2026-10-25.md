## 1. 设置面板重构（S1 → S3）

### S1：光标宽/高并入刻度表

原来光标宽度、高度是 3 处手写的 `row.slider(...)`，与其他 11 个滑块写法不一致。
并入 SPECS 数组成为 `SPECS[11]` / `SPECS[12]`，手写滑块从 3 处降到 1 处
（唯一剩下的那处在 `addSlider` 内部，是正常的）。

### S3：createPanel() 拆组

从 **465 行的一个大 lambda** 拆成 11 个私有方法，`createPanel()` 降到 **50 行**：

```
buildVersionRow / buildPresetRows
buildMasterGroup   总开关
buildInlineGroup   单行输入输出 + 行内预览
buildCrossGroup    多行缎带 + 跨行预览
buildColorGroup    颜色
buildCursorGroup   光标（宽 / RGB / 高）
buildGlowGroup     辉光
buildFadeGroup     淡出
buildExperimentalGroup  实验性
buildDiagGroup     高级诊断
```

新增一组 = 写一个方法 + 加一行调用。

#### 踩坑：组的渲染顺序不是源码书写顺序

原版把「光标」组的 `panel.group(...)` 写在「辉光」组的 lambda 体**内部**
（用的是 `panel` 而不是 `g`，所以是同级）。但 `DialogPanel.group()` 是
**等回调跑完才把组挂到父容器**的 —— 内层先挂、外层后挂，实际渲染顺序是：

```
颜色 → 光标 → 辉光 → 淡出
```

我一度按源码观感写成「辉光 → 光标」，顺序一变，全部控件的遍历索引跟着挪，
探针里按固定索引定位的地方立刻串台（VRegr2 的 R-8 变好、R-11 变坏）。
已显式把光标组放回辉光之前，并在代码里写清这条约束。

#### 验证手段：组件树逐位比对

只比「有多少个滑块 / 复选框」会掩盖顺序差异（第一版就是这么漏掉的，
因为对比脚本把两边清单都排序了）。改成把整个面板按
「路径 + 深度 + 内容」dump 出来逐行 diff —— 重构后 79 条条目与重构前
**路径、深度、文本全同**。

## 3. 性能调查（结论：仪表是坏的）

### 先纠正仪表

用户据日志认为「多光标掉到 58fps」。用时间戳重算真实帧间隔：

| 光标数 | 每帧 | 真实 fps |
|---|---|---|
| 1 | 8.00ms | 125 |
| 5 | 8.00ms | 125 |
| 8 | 8.53ms | **117** |

**平滑始终满帧。** 所谓 58fps 是统计口径错误（采样次数当帧数，少算 15 倍）。

### 真正的问题是长尾

8 光标时分位数：`p50 = 8.5ms，p90 = 17.9ms，p99 = 44.1ms`。
73 个样本里 14 个慢帧，**其中 13 个是 `offsetMoved=true`（拖尾正在动）**。
即：卡顿来自拖尾运动瞬间的偶发 40ms+ 停顿，不是平均帧率低。

### 绘制成本实测（生产代码，每档 3000 帧均值）

**关键发现：真正放大成本的是 stretchRatioK，不是光标高度。**

| 光标数 | 拉伸 k | 每帧绘制 | 占 8ms 预算 |
|---|---|---|---|
| 8 | 1.0 | 1166µs | 14.6% |
| 8 | 2.0 | 1793µs | 22.4% |
| 8 | 4.0 | 3020µs | 37.7% |
| **8** | **8.0（用户设置）** | **5416µs** | **67.7%** |

用户的 `stretchRatioK = 8.0`（缎带档上限）+ `glowLayers = 8`，
8 光标时辉光绘制单独吃掉 **68% 的帧预算**。

这也解释了「原版粉色也卡过」：换颜色不改变绘制量，**拉伸强度才改变**。

### 已删除的两个优化尝试

1. **描边代替填充**：实测反而慢 6%（0.94x）。Java2D 的 `draw` 要先构造
   stroke 几何再填充，比 `fill` 多一步。
2. **辉光层数自适应降级**：被用户否决（与已有开关语义重复，且写在它的
   else 分支里导致开关一勾就失效）。

## 4. 参数职责梳理（回答"到底哪个对"）

用户的疑问：单行不拉伸、跨行很长、预览窗单行却很夸张 —— 到底哪个对？

**答：实际使用是对的，预览窗失真。**

### 两套分支的真实算法

短跳判据：`sameLine && charsMoved <= 3`

**单行**（读 trailFactors）：

```
animationLength = shortAnimationLength × trailFactors[rank]
用户参数(k=8, smooth=0.2) → 四角 [110, 81, 50, 29] ms
```

**跨行**（完全不读 trailFactors）：

```
leading  = animationLength × (1 - trailSize)
trailSize = 1.0 ⇒ leading = 0
用户参数 → 四角 [280, 140, 0, 0] ms
```

前缘两角**瞬时吸附**，后缘拖 280ms → 不规则四边形，非常明显。

### 预览窗为什么夸张

预览每帧把光标从 A 点整体跑到 B 点，用**整段行程**展示拉伸；
真实单行每帧只挪**一个字符宽**、且最短角也有 29ms（约 3.6 帧）。
即：预览把「跨行」的大位移套在了「单行」的标题下。
