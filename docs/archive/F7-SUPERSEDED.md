# F7 已被取代 —— 为什么现在没有 F7 补丁可摘

> 写于 2026-10-27。
> 结论：**F7 修完了，而且它修的那个 bug 已经随预设模型重构一起消失了。**
> 本文给后来接手的人一份交代：这条 bug 是什么、当时怎么修的、为什么现在不可能再犯、
> 原来守它的 7 条断言现在由谁接管。

---

## 一、F7 是什么

F7 是一条**静默销毁用户工作**的路径。它的可怕之处在于：每一步看起来都正常，
没有任何报错，用户的改动就是这样一点点没掉的。

原始描述（引自提交 `a19e402` 的 body）：

```
1) 用户在面板把「缎带」跨行时长改成 0.15 → apply → 写进覆盖表
2) 用户从 Tools 点「缎带」→ 修复前把 13 项改回预设常量，用户的改动被冲掉
3) 用户再在面板点「应用」→ current == constants 成立 → removeOverride
   → 覆盖值被删除，改动永久丢失
```

关键在于 **0.9.8 的预设模型**：每个内置预设各自记着一份「用户在它上面的改动」
（覆盖表 `animPresetOverrides`）。面板点预设走 `onAnimPresetPicked()`，会先读覆盖表；
而 Tools 菜单的 `applyAnimPreset()` **直接写预设常量**，绕过了覆盖表。

两个入口对同一份数据给出不同的结果 —— 这就是四-J 说的
「同一份语义存在于两处」，不是补丁能修的，是模型本身有问题。

## 二、当时怎么修的

两版，都在历史里：

| 提交 | 分支 | 内容 |
|---|---|---|
| `a19e402` | `feat/settings-ui-ready` | 0.9.9 版，13 项字段域 |
| `ca48301` | 当前分支（`fix/f7-override-read`） | 0.9.8 基线版，6 项字段域 |

修法一致：`applyAnimPreset` 先查覆盖表，有覆盖用覆盖值，没有才用预设常量；
并同步前移 `animPresetBase`；新增 `indexOf(AnimPreset)` 辅助方法。

**0.9.8 基线版就在当前分支历史里**：`git merge-base --is-ancestor ca48301 HEAD` 返回真。

## 三、为什么现在不可能再犯

`bc903e1`（2026-10-22）把预设模型整体换掉了。新模型：

```
内置预设 = 永久只读的常量表
用户改动 = 自动派生到「X 副本」（自定义预设）
```

这是 GIMP / IntelliJ 配色方案同款模型。它让整个覆盖表机制失去了存在理由：

- `CursorPresets.java:383` 原文：
  > 【0.9.88 删除：预设覆盖值机制（177 行）】…
  > 三个方法在生产代码里零调用，仅剩两处 javadoc 的 `{@link}` 引用
- `CursorPresetApplier` 的 javadoc 原文：
  > 0.9.9 起不再读覆盖表：内置预设**永久只读**，用户改动一律落在自定义预设上…。
  > 所以本方法只写那 6 个预设常量，不存在「冲掉用户改动」的可能 ——
  > **0.9.8 的 F7 那条数据销毁路径随模型一起消失。**

也就是说：**不是修好了，是这条路径在地图上不存在了。**
用户在「缎带」上改的任何东西都落在「缎带 副本」里，从 Tools 点「缎带」
只会动那个只读常量，碰不到副本，用户的数据连被访问的机会都没有。

## 四、原来那 7 条断言现在由谁守

`VOverride` 探针随机制一起被删了（`bc903e1` 里 `VOverride.java` 减少 121 行）。
它断言的 `parseOverride` / `putOverride` / `animPresetOverrides` 三个 API 已全部不存在。

但**语义没有丢**，等价守护散在 `VCustom` 里：

| 原断言 | 现在由谁守 |
|---|---|
| F7-1 有覆盖时跨行时长 = 0.15（不是常量） | `VCustom` C-15（应用内置预设只写 6 个动画字段，值 = 预设常量） |
| F7-2 覆盖里的辉光层数 3 被采用 | `VCustom` C-15 + `VDefaultFreeze` F-5 |
| F7-3 覆盖串应用后仍然存在 | 机制已删，无直接对应；由 `C-18`「应用内置预设不删除任何自定义预设（用户数据不丢）」覆盖同等语义 |
| F7-4 基准下标前移到该预设 | `VCustom` C-17（清空「当前自定义」指针，回到内置） |
| F7-5 无覆盖的预设仍按常量全量覆盖 | `VCustom` C-15 / C-16（正交性硬判据：不动颜色） |
| F7-6 【关键】不会触发 removeOverride | `CustomPresets` 里根本没有 removeOverride 这条调用路径 |
| O-0 前置：覆盖值可被 parseOverride 解析 | 机制已删，无对应 |

**F7-6 是最值得说明的一条**：它守的是「覆盖保得住」。新模型里用户的完整参数快照
存在 `CustomPresets` 里，走的是「保存 / 重命名 / 删除」三个显式操作
（`VCustom` C-6 ~ C-14 守着）。没有任何隐式路径会删它 —— C-18 就是直接断言这一点的。

## 五、怎么自己复核

三条命令，都能直接跑：

```bash
# 1. 确认生产代码零引用覆盖表
#    期望：只有 2 条命中，且都是【注释】——
#      CursorPresets.java:383      删除说明
#      NeovideCursorConfigurable:2291  javadoc 里的 {@link}
#    若出现第 3 条（或在非注释位置），说明机制被加回来了。
grep -rn "animPresetOverrides\|parseOverride\|putOverride" src/main/java/
```

```bash
# 2. 确认 F7 的 0.9.8 版修复确实在历史里（应输出「是」）
git merge-base --is-ancestor ca48301 HEAD && echo "是" || echo "否"
```

```bash
# 3. 看新模型的官方说明（代码里的原话，不是本文的转述）
sed -n '380,392p' src/main/java/com/github/yyyolo7a79/neovidecursor/settings/CursorPresets.java
```

第 1 条如果**超过 2 条命中**，或命中落在非注释位置，说明有人把覆盖表加回来了 ——
那时本文作废，要么按老路重新守 F7，要么先想清楚为什么要回退模型。

## 六、为什么不再单独产出一个 F7 jar

原任务书要求「产出可独立构建的 jar 放 `dist/`」。不做的原因：

- 没有代码改动可打包 —— 修复早已在 HEAD 里
- 当时的产物意义是「让用户能只装 F7、不装别的改动」，而**现在没有「别的改动」**
- `dist/` 目录当前不存在，且被 `.gitignore:36` 忽略

如果将来真的需要「只含 F7 的基线包」，做法是从 `ca48301` 拉分支构建，
而不是从当前 HEAD 往回摘。
