**目标归纳**：

1. 辉光要**跟着拖尾一起变暗**（不是停下后才开始）；
2. 两个淡出参数（保持时长 / 淡出时长）必须**真的有效**；
3. 不能出现**突兀消失**；
4. 不要按层数做变暗（8 档跳变，算改手感）；
5. 不要影响其他手感（连续打字、跨行、多光标）。

## 四、已确认的根因

### 4.1 「淡出」在旧版里根本看不见（报告 §14.2 实测）

`docs/archive/reports/FIX-INPUT-FADE-REPORT-2026-11-01.md` §14.2（FadeDiag 逐帧采样）：

```
   0ms  fade=1.000  glow=1.000
 277ms  fade=1.000  glow=0.015     ← 弹簧收拢，亮度已接近 0
 812ms  fade=0.965  glow=0.015     ← 保持期结束，开始"淡出"
1750ms  fade=0.027  glow=0.000
```

旧实现把「最后一次可见帧的亮度（≈0.015）」当淡出起点，等于「从 1.5% 淡到 0」。
**这是用户最初报「淡出改到 500 没效果」的真正原因**，也是「用了很久的手感」的真实样子：
辉光跟着拖尾一起消失，没有可感知的尾巴。

### 4.2 0.9.118 的回归（跨行中途灭）

`4af8965` 把淡出计时绑到 `moved`（只持续 1 帧），跨行拖尾要展开 400+ms：

| 场景 | 拖尾可见 | 辉光画到 | 无辉光占比 |
|---|---|---|---|
| 基础 0.10s | 152ms | 120ms | 21% |
| 缎带 0.28s | 424ms | 120ms | **72%** |

版本边界（`javap` 对比 dist 内 jar）：`needsMoreFrames` 在 0.9.116/117 不存在，0.9.118 起存在；
`git log -S needsMoreFrames` 唯一命中 `4af8965`。

### 4.3 0.9.123 的闪灯（跳变）

收拢那一帧把保持值从曲线残余（≈0.02）钉到 `1.0`：亮度是**阶跃**，
于是「先暗→突然亮→再淡出」。用户描述「闪两下再暗」与代码一致。

### 4.4 0.9.125 为什么仍突兀（绘制层分析，本轮新发现）

见 §五。一句话：**同样的 75ms 线性 alpha，作用在已经缩到最小的光晕上，
比作用在拉伸中的大光晕上显得突兀得多**。

## 五、绘制层事实（决定「突兀感」的物理原因）

### 5.1 辉光是 8 层同心外扩，层数不是亮度轴

`CaretTrailPanel.drawQuadGlow()`：

```java
float peak = config.glowOpacity * (glowColor.getAlpha() / 255f)
        * quadGlow * glowFade;                       // :1000-1001
double layerAlpha = 1.0 - Math.pow(1.0 - peak, 1.0 / layers);  // :1009
```

- 每层半径 `radius = glowWidth * i / layers`（线性分布），从外向内绘制；
- 每层 alpha 由上式的 **N 次根**反解，保证 N 层叠加后的累计不透明度 = `peak`；
- **层数只决定离散粒度/平滑度，不改变整体亮度**。`NeovideConfig.java:40-59` 明确写了这一点；
  若强行「按层数减」，只有 n=0..8 共 9 个离散档位（0.550 / 0.503 / 0.451 / 0.393 / 0.329 /
  0.259 / 0.181 / 0.095 / 0），最后一下仍是硬切。**不要按层数做淡出。**

### 5.2 线性 alpha 在感知上「前慢后快」

默认 `peak=0.55`、8 层时，最外层单层 alpha ≈ 24/255（9.5%）：

| 淡出进度 | 时间（75ms） | 峰值 | 外缘单层 alpha | 约 1px 内圈累计 |
|---|---|---|---|---|
| 1.00 | 0ms | 0.550 | 24/255 | 0.490 |
| 0.50 | 37.5ms | 0.275 | 10/255 | 0.238 |
| 0.25 | 56.3ms | 0.138 | 5/255 | 0.118 |
| 0.125 | 65.6ms | 0.069 | 2/255 | 0.058 |
| 0 | 75ms | 0 | 0 | 0 |

**外圈 4~5px 在前 40~55ms 就低于可见阈值，最后约 20ms 只剩 1px 内核在掉**；
再叠加 8ms/帧只有 9 帧、EDT 抖动可能只剩 4~6 帧 → 主观就是「停一下，然后突然没了」。

### 5.3 光晕面积不会缩到 0，但会缩 15%~41%

`glowWidth = shadowBlurFactor × max(光标宽, 高)`，按**光标名义尺寸**算，不随拉伸变化
（`updateGlowRadius`）。所以收拢时：

- 跨行 32px 拉伸 → 收拢：可见环面积约 `1009 → 599 px²`（−41%）；
- 同行 8px 位移 → 收拢：约 `701 → 599 px²`（−15%）。

0.9.120 的淡出作用在**大而拉伸**的光晕上；0.9.125 把它推迟到**已经缩到最小**的光晕上。
同样的曲线，后者观感更接近「突然熄灭」。**这是 0.9.125 加了 50ms 保持反而更突兀的原因。**

### 5.4 重绘不是问题

`computeTrailBounds` + `submitRepaint` 会把上一帧脏区与本帧区域合并重绘，面板 `setOpaque(false)`，
旧光晕会被正确擦除。**没有任何「上一帧光晕残留后突然消失」的证据。**

唯一相关边缘：`glowPadding = ceil(glowWidth)+4`，默认 6.4px 时 `11 > √2×6.4≈9.05` 安全；
若 `shadowBlurFactor` 拉到 0.6（glowWidth=19.2），`pad=24 < 27.2`，可能裁掉光晕边缘
（源码自己写了这条警告）。**默认参数下不是本问题成因。**

## 八、候选方向（待用户拍板）

### A. 只调参数（零代码）

保持 0.9.125，把「淡出时长」拖到 300~500ms。代码不改；「停下后才灭」不变。
**这是最快能验证「是否只是时长太短」的方法。**

### B. 限速变暗（推荐方向，需改代码）

亮度目标仍是 `strengthFor(偏移)`；把「到点乘 0」换成**限制下降速度**：

```
每帧最多下降 = dt / 淡出时长
拖尾展开期间：目标 = 曲线值，亮度只能以该速度逼近
完全收拢后：先等「保持时长」，再以同一速度降到 0
```

效果：拖尾收拢时亮度就开始降（跟着一起暗），但不会被瞬间掐掉；
「淡出时长」直接决定降多慢（75ms / 500ms 观感明显不同）；
全程连续、无跳变。需要按组维护亮度状态（多光标时不串扰），并重写调度与探针。

**风险**：替换现有淡出计时是一次中等重构（3 个生产文件 + 2 个探针），
必须配套变异测试，防止「又改坏了别的」。

### C. 感知线性曲线（可与 A/B 叠加）

把 alpha 曲线从线性改成 `alpha = (1-t)^3`（前段掉得快、末尾拖长），
让外圈先淡出、内核留到最后，观感更柔和。只改一个乘法公式，不动几何与层数。

### D. 不改层数

用户已明确：按层数变暗算改手感（连续打字时更不可控），不采用。
仓库文档（`NeovideConfig.java:40-59`、`UPSTREAM-PITFALLS.md:636`）也把层数定义为平滑度。

## 十、给接手者的三条硬提醒

1. **任何改动都必须能解释「突兀感」这一层**：只测 fade 数值不够，要看 alpha 的感知曲线
   和光晕面积。报告 §5 的表格可以直接拿来对照。
2. **不要再往「收拢帧钉满亮」方向走**（0.9.123 的闪灯教训），也不要做按层数变暗。
3. **每次改动四段输出**：红 → 绿 → 变异红 → 恢复绿；门禁只跑一份；D0 必须零 diff。
