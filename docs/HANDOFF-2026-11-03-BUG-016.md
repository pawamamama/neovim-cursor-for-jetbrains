## 三、为什么「修 bug」会把三个预设的手感都改掉

关键数字（`shortAnimationLength=0.11`，`trailSize=1.0`）：

| 预设 | animationLength | 跨行 rank0（后缘） | rank1 | rank2/3（前缘）修前 | rank2/3 修后 |
|---|---|---|---|---|---|
| 基础 | 0.10s | 100ms | 50ms | **0ms（瞬移）** | **55ms** |
| 缎带 | 0.28s | 280ms | 140ms | **0ms** | **55ms** |
| 纯平滑输入 | 0.10s | 100ms | 50ms | **0ms** | **55ms** |

- 修前的 0ms 不是 bug，是**缎带形状的来源**：前缘立刻咬住新位置、后缘慢慢拖出去，
  中间的四边形才是「拖尾」。
- 修后前缘要跑 55ms，前后缘一起慢 —— 四边形在最初的 55ms 里变窄，
  观感就是「拖尾变小 / 密度没了」。
- 更糟的是**这个下限与 animationLength 无关**：
  - 对缎带（280ms）只占 20%，勉强能接受；
  - 对基础 / 纯平滑（100ms）占 55%，前缘从「瞬移」变成「比 rank1 还慢」，
    所以「三个预设都变了」，且短动画预设变化最大。

**一句话**：我们把「误判成跨行」和「真正的跨行」共用的那支画笔改了。
真正的跨行本来就该是 0ms 前缘；修完以后，正常跨行也被改了。
正确的做法是**只改误判那一条路**，不动真正的跨行。

## 四、下一步修复方案（推荐 A）

### 方案 A：给「同一行内的连打/删词」单独一条分支，保留真跨行的 0ms 前缘

现状判据（`TrailCorner.jump()`）：

```java
boolean isShortJump = sameLine && charsMoved <= config.typingMaxChars; // 3
if (isShortJump) { 时长 = shortAnimationLength × trailFactors[rank] }
else            { 跨行三档：leading = animationLength × (1 - trailSize)，trailSize=1 → 0 }
```

问题：`charsMoved` 是**帧间累计量**（`SpringTrail.updateCharsMoved`）。
一帧内落进 4+ 次击键（连打、Ctrl+Backspace、帧稀疏合并）就 >3 → 掉进跨行分支 →
前缘 0ms 瞬移、后缘 animationLength（基础 100ms / 缎带 280ms）——
用户看到的「同一个按键，这次有拖尾、下次没有」。

推荐改法：**新增第三类「同一行的连续移动」**，而不是给跨行加下限：

```java
boolean sameLine = Math.abs(deltaYpx) <= height * 0.5;
boolean isShortJump = sameLine && charsMoved <= config.typingMaxChars;   // 保持
boolean isHorizontalBurst = sameLine && !isShortJump;                    // 新增

if (isShortJump || isHorizontalBurst) {
    // 短跳分支（同一支画笔）：时长 = shortAnimationLength × trailFactors[rank]
    // 可选：isHorizontalBurst 时把 rank0 的上限放到 min(animationLength, short×1.5)，
    //       避免长距离同行移动时尾巴太短
} else {
    // 真跨行 / 大跨度：leading = animationLength × (1 - trailSize)  ← 原样，0ms 保留
}
```

要点：
- **真跨行（`sameLine == false`，上下/换行/鼠标大跳）完全不受影响**，0ms 前缘保留 →
  缎带密度回来。
- 受影响的只有「同一行内移动 >3 字符」这一种，正是会被误判的连打/删词；
  它得到的时长与短跳同源（`shortAnimationLength × factors`），
  对基础 = 110/79/46/24ms，对缎带 = 110/76/39/14ms（系数随 k 变），
  比「0 / 100 / 50」至少不会把尾巴整个抹掉，也不会改变真正跨行。
- 若担心同行大跳（Ctrl+End）尾巴太短，可在 `isHorizontalBurst` 里把 rank0
  时长抬到 `max(short×factor, min(animationLength, short×1.5))`；**先不加**，
  按最小行为变化验证。

### 方案 B：整体回退前缘下限，承认「误判」是既有行为

如果用户认为「跨行密度」比「连打时偶尔没拖尾」更重要，就回退 `aeff707` 里
TrailCorner 的那一行（`git revert` 或手动删 `Math.max`），保留：
- 像素复查（B）；
- install.ps1（C）；
- 面板文案改回（中英资源）；
- `VTypingSpan`：T-1/T-2 会红，需要按「契约恢复」改回原断言方向，
  **不要删断言**（纪律二.6）。

### 方案对比

| | A（同一行 burst 单独分支） | B（整体回退） |
|---|---|---|
| 真跨行密度 | 恢复 | 恢复 |
| 连打时拖尾 | 稳定（有短跳形的尾巴） | 回到「有时有、有时没有」 |
| 改动面 | TrailCorner 判据 + 一条分支 + 探针 | 删一行 + 文案/探针回退 |
| 风险 | 同行大跳的尾巴可能偏短（可用上限兜） | 原 bug 保留 |

**推荐 A。** 它把「修复」限制在真正出问题的那条路径上，符合
`docs/WORK-DISCIPLINE.md` 四-J「名字与行为一致、同一语义不要两处」的判据。

    isHorizontalBurst = sameLine && !isShortJump;
