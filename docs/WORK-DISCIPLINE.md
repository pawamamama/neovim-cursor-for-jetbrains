### 13. 加 UI 控件必须先问（2026-10-25 用户要求）

**用户原话：「加功能要问我控件加不加」。**

**我犯过：** 0.9.78 发现 `targetFps` 字段接通了调度却没有控件入口，
我直接加了个「目标帧率」下拉框（125 / 144），没问过用户。

- 面板已经很长，多一项就多一分拥挤
- 用户可能宁愿写死在 125，或在别处（Tools 菜单）暴露
- 控件一旦发布就是用户可见的承诺，删掉比加上难

**正确做法：**
1. 技术问题自己修（把字段接进调度、补探针）
2. **「要不要给用户一个可见入口」先问**，给出选项与代价
3. 等用户说「加」再动面板

**判据：这个改动会不会出现在用户眼前？** 会，就问。

## 四-B、状态字段的三层拷贝（2026-10-24 血泪教训）

> **【2026-10-28 口径说明】** 本节的三层（声明 / FIELDS / copyFrom）是**持久化回路**，
> 记录的是 2026-10-24 当时真实踩过的坑，**不要改动本节正文**。
> 今天做功能请按 **六层** 走（上面三层 + ④ `loadState` + ⑤ 消费者 + ⑥ UI 控件），
> 完整口径与「哪几层已自动化」见 `CLAUDE.md` 陷阱 2 与 §7.0 落点清单。
> 只按四层做，最典型的后果是「值全对但界面没反应」—— 即 `targetFps` 那次事故。

**问题**：诊断日志勾选后，一点应用就消失。查了两轮才修完。

**这个 bug 的教训值得单独成节，因为它暴露了一个系统性陷阱：**

### 加一个 State 字段，必须同时改 3 处

| # | 位置 | 漏了会怎样 |
|---|---|---|
| 1 | `State` 字段声明 | 编译不过（最容易发现） |
| 2 | `SettingsField.FIELDS` 表项 | **`apply()` 遍历表时不拷贝 → 一应用就回滚** |
| 3 | `State.copyFrom()` | **`pending = deepCopy(state)` 时丢值 → 复选框永远不勾** |

**第 2、3 层都是「静默失败」——不报错、不抛异常，只是值不见了。**

我第一次只修了第 2 层，用户说「不能」，才发现还有第 3 层。

### 正确的检查命令（加字段后必跑）

```powershell
# 检查 State 所有字段是否都在 copyFrom 里
cd D:\deepseekwork\neovim-cursor-pr
$f = "src\main\java\...\NeovideCursorSettings.java"
$src = Get-Content $f -Raw
$fields = (Select-String -Path $f -Pattern '^    public (boolean|int|float|String) ([a-zA-Z]+) =' |
    ForEach-Object { $_.Matches[0].Groups[2].Value })
foreach($n in $fields){
    if($src -notmatch ("$n = from\.$n")){ Write-Host ("❌ copyFrom 缺: " + $n) }
}
```

**没有输出 = 全部字段都在。**

### 同理：SettingsField.FIELDS 也要核对

```powershell
# State 有但 FIELDS 没有的字段 = apply 永远不拷贝
```

### 判断一个新字段该怎么接

| 字段类型 | 要改哪些地方 |
|---|---|
| 只进 State（如 `diagLogging`） | State + FIELDS（CONFIG 两参传 `null`）+ copyFrom |
| 同时进 CONFIG（大多数观感参数） | 上面 3 处 + CONFIG 字段 + FIELDS 的 config 映射 |
| 派生量（如 `trailFactors`） | **不进 FIELDS**，在 `syncStateToConfig()` 里单独派生 |

## 四-D、一个字段承担两个职责 = 定时炸弹（2026-10-24）

**同一个 bug 我修了两次，中间隔了 35 个版本。**

### 时间线

| 版本 | 我做了什么 | 后果 |
|---|---|---|
| 0.9.21 | 让块选区所有行**共享**同一个 `charsMoved`（修加速度不均） | ✅ 加速度修好了 |
| 0.9.56 | 发现多光标横向拉伸是单行的 2.5 倍 | ❌ 上一步**弄坏**了分支判定 |

### 根因

`charsMoved` 这一个值承担了**两个职责**：

```java
// TrailCorner.jump() 里
isShortJump = sameLine && charsMoved <= typingMaxChars(3);
//         ↑ 职责1：选分支（短跳 vs 跨行），决定用哪个时长字段
```

```java
// 加速度判定也用它
animationLength = config.shortAnimationLength * trailFactors[rank];
//                    ↑ 职责2：影响四角时长的相对关系
```

**0.9.21 我把块选区的 `charsMoved` 从「每行各算」改成「共享一个大值」，修好了职责 2，却让职责 1 判错了。**

块选区的 offset 差跨行时天然几十上百，必然 > 3 → 被判成跨行 → 用 `animationLength`(0.28) 而不是 `shortAnimationLength`(0.11) → 拉伸暴涨 2.5 倍。

### 教训

**当一个值同时参与「分支选择」和「数值计算」时，改它之前必须先问：另一个职责会怎样？**

正确的做法是**拆成两个参数**：
- `charsMoved` → 只用于加速度计算
- `deltaY / height` → 只用于分支判定

这次没拆，改用「块选区传 -1 走归一化分支」绕开 —— 能用，但**下次动这块代码时要注意**。

### 检查清单

改任何「共享量」之前：

```powershell
# 1. 这个值被哪些地方读？
grep -n "charsMoved" src/main/java/**/*.java

# 2. 每次读取是「分支判断」还是「数值计算」？
#    两者混用 → 必须拆参数，不许共享
```

## 四-E、字段接通了 ≠ 字段生效了（2026-10-25，最严重的一次）

**这是本项目探针体系的系统性盲区，不是漏了一条断言。**

### 事故

0.9.76 我加了 `targetFps` 字段（125 / 144），当时链路看起来完整：

```
State 声明        ✓
loadState 拷      ✓
copyFrom 拷       ✓
SettingsField     ✓（含白名单校验）
```

四条都做了，探针也全绿。**但 `CaretAnimator.computeNextDelayNs()` 读的是常量**，
从来没读过这个字段 —— 用户选 144 完全没有效果，是纯死字段。

### 更糟的是：我在文档里写下了错误的结论

`PERFORMANCE-FPS.md` 写着「144fps 实测 143.5，精准达成」。
那个数字测的是 **裸睡眠循环**，不是生产路径。

**做基准和用结论是两件事**：基准证明「系统睡眠精度够」，
不等于「插件会按这个精度调度」。我把前者当成了后者。

### 三条探针为什么全都没抓到

| 探针 | 验证什么 | 为什么抓不到 |
|---|---|---|
| `VLoadState` | 往返不丢 | 存进去就通过 |
| `VDefaultFreeze` | 默认值没变 | 跟使用无关 |
| `VAddSetting` | 进了 FIELDS | 跟使用无关 |

**全部只覆盖「持久化链路」，没有一条覆盖「消费链路」。**

### 修法与守门

新增探针 `VDeadField`，核心一条：

```java
// 读方法体源码，检查它是否真的引用了字段
int m = src.indexOf("private long computeNextDelayNs");
String body = src.substring(m, end);
check("computeNextDelayNs 体内引用了 targetFps",
      body.contains("targetFps") || body.contains("activeDelayNsForTarget"));
```

### 加字段时必须问的第四个问题

四-B 那节说「加字段要同步 3 处（声明 / FIELDS / copyFrom）」。
**现在要加第 4 问：谁消费它？**

```powershell
# 加完字段，必须能看到「读」的地方，不能只有「写」
grep -n "targetFps" src/main/java/**/*.java
# 期望结果里必须有：声明 / loadState / copyFrom / FIELDS / ★ 消费者代码
# 如果全是写、没有读 -> 死字段
```

### 顺带：字段通了 UI 也可能断

同一次审查还发现：`targetFps` 接进调度之后，**设置面板里根本没有控件**。
字段通到底了，UI 断了，用户依然无从选择。

**所以加字段实际是 5 处**：声明 / loadState / copyFrom / FIELDS / 消费者 + UI 控件。

## 四-F、基准数据 ≠ 端到端结论（2026-10-25）

**同类错误我犯过三次，每次都是「把局部测得的数据当成整体结论」。**

| # | 当时的结论 | 实际 | 错在哪 |
|---|---|---|---|
| 1 | 「改成描边更快」 | 慢 6% | 基准只测 fill/stroke，没测真实绘制路径 |
| 2 | 「8 光标掉到 58fps」 | 117fps | fps 统计本身少算 15 倍 |
| 3 | 「144fps 精准达成」 | 生产路径恒 8ms | 基准测裸循环，没接生产调度 |

### 纪律

写进文档的性能数字，必须标明**测的是什么**：

```
✓ 「裸 sleep 循环能达 143.5fps」（基准，tools/bench/）
✓ 「8 光标 RGB 绘制 246µs」（基准，单帧绘制）
✓ 「诊断日志显示 fps=117」（端到端，真实运行）

✗ 「插件能跑 144fps」   ← 没有端到端证据就不要这么写
```

**端到端结论只能来自诊断日志或用户实测，不能来自基准。**

## 四-G、探针本身会骗你：两种假通过（2026-10-25）

### 假通过 A：探针读的是死数据

`CaretTrailPanel.cornersForProbe()` 读 `polyX/polyY`，
而那对数组在多光标重构后**恒为初值 0**（生产代码全走 `addQuad`，
`updateCorners` 变成零调用，只剩三个探针还在用它）。

于是探针读到 8 个 0，却「验证通过」—— **假的安全感**。

### 假通过 B：探针复刻了逻辑而不是调用生产代码

`VRankCollapse` 第一版自己实现了一遍排序来验证 rank，
**没有调用生产代码的 `assignRanks()`**。

后果：`idxScratch` 复用的隐式顺序依赖 bug，探针抓不到。

### 纪律

1. **探针必须读「绘制/调度真正用的那份数据」**，不是旁边的影子副本
2. **探针必须调用生产方法**，不许自己实现一遍算法再验证自己的实现
3. 判断方法：把这个字段/方法改坏，探针**必须红**。不红就是假通过

```powershell
# 验证探针有效性的标准做法：变异测试
# 1. 故意改坏生产代码一行
# 2. 跑探针，期望它红
# 3. 恢复，确认全绿
# ★ 变异测试后必须删 classes 目录全量重编译
#   否则 javac 增量编译复用旧 class，你测的是旧字节码
```

> 这条是真踩过的坑：变异测试恢复源码后没重编译，
> 探针报「登记=1」、VerifyPanel 也红，我一度以为源码真的丢了绑定，
> 用 `javap` 反编译才确认字节码里两个都在。

## 四-G-2、三种假象：假通过、假失败、并发假红（2026-10-25 深夜）

四-G 讲了「探针会骗你」的两种**假通过**。这一条补第三种，以及一类完全相反的：
**证据本身是假的，但方向是「假红」** —— 它会让你去修一个不存在的问题。

### 假象三：并发跑门禁 → 假失败

**现场**（2026-10-25 深夜，本轮真实发生）：

```
主会话跑一次门禁 → 19 个探针未通过
子代理同时也在跑 → 它报「18 个未通过」
两个人都以为自己引入了回归，差点回滚已有的正确修复。
```

**根因**：两份门禁共用 `build\v2-probe\classes`。
编译那一步会先 `Remove-Item classes` 再重建 —— 另一份正在加载探针主类时，
目录被清空 → `ClassNotFoundException: SpringTrail` → 探针集体崩。

**症状特征**（用来识别）：
```
· 失败数突然暴涨（8 → 18 / 19）
· 失败里混着根本没被改过的探针
· 报错是 ClassNotFoundException / NoClassDefFoundError，不是断言 FAIL
· 换个目录重跑，数字立刻回到正常
```

**规则**：
1. **一份门禁一个目录。** 并行跑就给每个进程独立的 `-Repo` / 输出目录。
2. **看到失败数暴涨，先重跑一次**，再判断是不是回归。
   重跑同一个数字 = 真回归；换目录后正常 = 并发假象。
3. **两个 agent 同时改同一个仓库时，门禁归主会话跑。**
   子代理改完自己那份就停，不要各自跑全量。

### 对应的纪律：证据要能区分「我造成的」和「本来就有的」

本轮子代理做了一件值得学的事 —— **控变量验证**：

```
c3bf6c9（本轮开始前）基线          → 9 个未通过（含 VReset）
HEAD + 它的改动                    → 8 个（VReset 变绿）
c3bf6c9 源码 + 仅它的改动（隔离）  → 9 个（VReset 回到 exit=1，其余不变）
```

第三行是关键：它在隔离树里装回旧版 `VReset.java`，证明
**「9 变 8」不是它的功劳，是另一次提交修好的**。

**没有这一行，就只能靠嘴说「不是我改的」** —— 那种话没人信，包括自己。

**规则**：改动涉及「某个数字变了」的结论，必须给出**控变量实验**：
```
① 改之前跑一次（基线）
② 改之后跑一次（结果）
③ 只装回旧的那一个文件再跑一次（归因）
```
三行数字摆出来，归因就是结论，不是观点。

### 变异测试：证明探针抓得住（四-G 第 3 条的补充）

本轮的正面例子（改 `VBlock` 后）：
```
把 trailSlotCount 的块选区分支改成读 caretCount  → K-3/K-5/K-7 三条红
把 blockTrailKey 改成返回固定常量                → K-4/K-6 两条红
恢复源码 + 删 classes 全量重编译                 → 全绿
```

**探针全绿不算证据，探针能被故意改坏的代码搞红才算。**

## 四-I、语义不清晰时必须先确认，不许猜（2026-10-25 用户明确要求）

**用户原话：**「添加一个明确决定 在用户语义不清晰时候必须确认用户的意图」

### 这一条是用一串严重失误换来的

整个 0.9.75~0.9.86 期间，我在「RGB / 彩虹 / 双拼 / 辉光」这四件事上连续猜错：

| 次数 | 我猜的 | 用户实际要的 |
|---|---|---|
| 1 | RGB 渐变升级成色相循环 | 一直是「拖尾色 → 算出的末端色」双拼 |
| 2 | 把双拼塞进纯色路径 | 双拼属于「光标渐变开关」 |
| 3 | 彩虹是「整条同一色相纯旋转」 | 沿长度多个色相 + 整条旋转 |
| 4 | `driftPhase` 是多余的「上下扫」该删 | 那是上游 wash 的核心机制之一 |
| 5 | 辉光跟随光标 | 从未存在过，一直是独立 shadowColor |
| 6 | `targetFps` 需要移到总开关组 | 早就在总开关组了 |

**六次猜错，每一次都做了实际改动，累计浪费数小时，用户情绪失控。**

### 判据：什么算「语义不清晰」

以下任一情况，**必须先问，不许动手**：

```
1. 用户用了模糊词：「改善」「好看点」「不对劲」「土」「怪」
   -> 问：具体是哪个维度？颜色 / 速度 / 形状 / 大小？

2. 同一个词在不同上下文可能有不同意思（如「混色」「动态」「渐变」）
   -> 问：你说的 X 是指 A 还是 B？

3. 用户说「改回去」「恢复」「应该还是那样」
   -> 问：改回到哪个版本 / 哪个状态？给两个候选让用户挑。

4. 我正要基于「用户大概是这个意思」做超过 20 行的改动
   -> 停下来，先把理解写出来让用户确认。

5. 用户的描述与我看到的代码/文档不一致
   -> 先读代码和文档，仍有矛盾再问。**不许直接按自己的理解改。**
```

### 问的方式

**给选项，不给开放式问题。**

```
✓ 「光标设置里那个开关，开 = 彩虹 还是 双拼？」
✗ 「你想要什么效果？」
```

**同时说明我为什么不确定**（一句话），让用户判断要不要展开：

```
✓ 「代码里 rgbGradient 同时被两处写，我不确定该归哪个 —— 是 A 还是 B？」
```

## 四-J、写代码看可维护性，不是「最小改动」（2026-10-25 用户明确要求）

**用户原话：**「写代码不要粗心只看最小改动，应该看可维护性」

### 这一条针对的是我的一个坏习惯

每次用户报问题，我的第一反应是「找一个改动最小的补丁」。
这在**单点故障**上是有效的，但在**设计问题**上会累积成屎山。

本项目的两个典型后果：

| 症状 | 我当时的「最小改动」 | 真正的代价 |
|---|---|---|
| RGB 渐变被换成色相循环 | 改一个 if 分支 | 形成 140 行死代码 + 功能与名字对不上 |
| 双拼放错位置 | 改 else 分支一行 | 占了纯色路径，用户所有颜色都带渐变 |

### 判据：什么时候不能只求最小改动

满足任一条，就该停下来做结构性修复：

```
1. 改动涉及「一个字段承担两个职责」
   -> 拆字段/拆枚举，别在分支里打补丁

2. 改动后同一份语义存在于两处（如两套清单、两份实现）
   -> 先统一成一处，再改

3. 改动让某个字段/方法的**名字与行为不符**
   -> 改名，别只加注释解释

4. 改动会产生死代码（删了调用但留着定义）
   -> 要么接回去，要么删干净，不许留着

5. 同一个 bug 第二次出现
   -> 说明前一次是补丁不是修复，重做
```

### 具体做法

改动前先问自己三个问题，写在 commit message 里：

```
1. 这次改的是什么层？(UI / 状态 / 绘制 / 物理)
2. 改完之后，还有谁在读这个字段/方法？语义还对吗？
3. 如果三个月后有人看这段代码，他能不能只看名字就理解？
```

**「最小改动」是优化目标，不是设计目标。** 设计目标是「改完之后不需要再改第二次」。

## 四-K、只有用户一个，没有老用户（2026-10-27 用户明确要求）

**用户原话：**
> 没有老用户目前就是我，我不会后台实现啊问我没有用

### 含义

本项目**只有一位用户**，就是项目作者本人。

因此：

- **不需要为「老用户的历史数据」设计迁移、兼容层、渐进式过渡**
- 遇到 `loadState`（加载已保存设置的方法）里的老值迁移逻辑，
  可以直接改成新语义，不必保留旧分支
- 一份代码只为一个「不存在的用户群体」服务，就是纯负担

**例外（唯一一条）**：用户自己机器上**已经存着的值**仍算老数据。
改默认值时要想清楚「他机器上那份怎么办」—— 是自动迁移、还是下次点预设覆盖。

### 判据

> **这段兼容代码是为谁写的？**
> 如果答案是「不存在的人」，删掉。

### 本项目的实际例子

`NeovideCursorSettings.java` 里的斜度迁移（`82 → 100`）原本的注释写着
「极少数恰好把滑块停在 82 的用户会被改成 100」——
那个「极少数用户」就是不存在的人。按四-K，这段逻辑可以直接简化。

> **这个问题如果答错，用户能看出来吗？**
> 看不出来就别问 —— 那是实现细节，不是产品决策。
